# MiniCPM5-2B vs MiniCPM-V-4.5 多维度基线对比测试报告

> **测试日期**: 2026-09-13 / 2026-09-14
> **对比模型**: MiniCPM5-2B-0822 vs MiniCPM-V-4.5（同 API 端点 api.modelbest.cn）
> **基线参照**: Kimi 2.5（2026-09-05 数据）
> **测试框架**: minicpm_e2e_test.py（真实高德 API 调用）
> **评估维度**: 8 维度 × 3 场景

---

## 一、执行摘要

| 指标 | MiniCPM5-2B-0822 | MiniCPM-V-4.5 | Kimi 2.5 (基线) |
|------|-------------------|---------------|-----------------|
| **端到端成功率** | 100% (3/3) | 100% (3/3) | 66.7% (2/3) |
| **总工具调用** | 22 次 | 20 次 | 39 次 |
| **平均响应时间** | 79.9s | **32.8s** | 130.6s |
| **平均迭代次数** | 4.7 次 | 2.0 次 | 3.0 次 |
| **高德 API 成功率** | 100% | 85.7% | 100% |
| **参数正确率** | 100% | 80% | 100% |
| **并行调用能力** | 弱（1-2 次/迭代） | **强（最多 12 次/迭代）** | 中（最多 12 次/迭代） |
| **工具调用格式** | 标准 function_call | 混合（function_call + 文本标签） | 标准 function_call |

**关键结论**：MiniCPM5-2B 在参数正确率和 API 成功率上优于 V-4.5，但 V-4.5 在响应速度（快 2.4x）和并行能力上显著领先。

## 二、场景级详细对比

### 场景 1：2 人烤肉（望京 + 霍营）

| 指标 | MiniCPM5-2B | MiniCPM-V-4.5 | 差异 |
|------|-------------|---------------|------|
| **状态** | 成功 | 成功 | 持平 |
| **迭代次数** | 6 | 2 | V-4.5 少 67% |
| **工具调用数** | 6 | 5 | 接近 |
| **执行时间** | 95.4s | **22.8s** | V-4.5 快 4.2x |
| **API 成功率** | 100% (6/6) | 60% (3/5) | 5-2B 优 |
| **参数正确率** | 100% | 60% (2 个 driving 参数错误) | 5-2B 优 |

**MiniCPM5-2B 执行路径**（顺序执行，每次 1-2 个工具）：
```
迭代1: geo(望京) + geo(霍营)                        → 2 calls
迭代2: search(烤肉)                                  → 1 call
迭代3: driving(望京→餐厅A)                           → 1 call
迭代4: driving(霍营→餐厅A)                           → 1 call
迭代5: driving(望京→餐厅B)                           → 1 call
迭代6: 生成推荐（刘记炙子烤肉）
```

**V-4.5 执行路径**（并行执行，一次多工具）：
```
迭代1: geo×2 + driving×2 + search                   → 5 calls（并行）
迭代2: 生成推荐（汉巴味德）
```

**V-4.5 参数错误**：destination 坐标为 `116411.0926,39.9774`（经度多出 `116` 前缀），导致 driving API 返回失败。5-2B 无此问题。

| **API 成功率** | 100% (7/7) | N/A（无 API 调用） | 5-2B 优 |
| **参数正确率** | 100% | N/A | 5-2B 优 |

**MiniCPM5-2B 执行路径**：
```
迭代1: geo×3（国贸、中关村、五道口）                 → 3 calls（并行）
迭代2: search(日料)                                  → 1 call
迭代3: driving×3（3 人→餐厅A）                       → 3 calls（并行）
```

```
迭代1: 输出 <queries>...</queries> 块（11 个工具调用）

```

**根因分析**：V-4.5 在此场景中退化为非标准输出格式（`<queries>` 标签），未使用 `<tool_call>` 或标准 `tool_calls`。这是模型行为不一致的表现——同一模型在不同场景下输出格式不同。

### 场景 3：2 人火锅（天通苑 + 三里屯，公平性推荐）

| 指标 | MiniCPM5-2B | MiniCPM-V-4.5 | 差异 |
|------|-------------|---------------|------|
| **状态** | 成功 | 成功 | 持平 |
| **迭代次数** | 4 | 3 | V-4.5 少 25% |
| **工具调用数** | 9 | 15 | V-4.5 多 67% |
| **执行时间** | 81.3s | **63.4s** | V-4.5 快 22% |
| **API 成功率** | 100% (9/9) | 100% (15/15) | 持平 |
| **参数正确率** | 100% | 100% | 持平 |
| **推荐餐厅** | 日坛涮肉四合院 | 海底捞火锅(牡丹园店) | 不同 |
| **路线计算** | 仅计算部分路线 | **计算全部 12 条路线** | V-4.5 更全面 |

**MiniCPM5-2B 执行路径**：
```
迭代1: geo×2                                         → 2 calls
迭代2: search(火锅)                                   → 1 call
```

```
迭代1: geo×2 + search                                 → 3 calls（并行）
迭代2: driving×12（2 人→6 餐厅，全部路线）             → 12 calls（并行）
迭代3: 生成推荐
```

**关键差异**：V-4.5 计算了所有 6 家餐厅的完整路线矩阵（2x6=12 条），而 5-2B 只计算了部分路线。V-4.5 的公平性分析更全面。

## 三、多维度能力评估

### 3.1 并行调用能力

| 维度 | MiniCPM5-2B | MiniCPM-V-4.5 |
|------|-------------|---------------|
| 最大并行数 | 3（geo×3） | **12**（driving×12） |
| 并行调用占比 | 32% (7/22) | **75%** (15/20) |
| 并行场景 | 仅 geo 层 | geo + route 全层 |
| 评级 | ⚠️ 有限 | ✅ 强 |

**分析**：V-4.5 的并行能力是 5-2B 的 4 倍。5-2B 基本是顺序执行（每次 1-2 个工具），而 V-4.5 能在单次迭代中发出 12 个并行调用。这是 V-4.5 响应速度快 2.4x 的主要原因。

### 3.2 参数提取准确性

| 参数类型 | MiniCPM5-2B | MiniCPM-V-4.5 |
|----------|-------------|---------------|
| 地址名称 | ✅ 100% | ✅ 100% |
| 城市参数 | ✅ 100% | ✅ 100% |
| 坐标格式 | ✅ 100% | ⚠️ 80%（偶发格式错误） |
| 搜索关键词 | ✅ 100% | ✅ 100% |
| 综合正确率 | **100%** | 80% |

**V-4.5 坐标错误案例**：`destination: "116411.0926,39.9774"`（经度字段多出 `116` 前缀，应为 `116.1109,39.9774`）。这种错误在 5-2B 中未出现。

### 3.3 工具调用格式兼容性

| 格式 | MiniCPM5-2B | MiniCPM-V-4.5 |
|------|-------------|---------------|
| 标准 `tool_calls`（OpenAI） | ✅ 始终使用 | ⚠️ 有时使用 |
| `<tool_call>` 文本标签 | ❌ 不使用 | ⚠️ 有时使用 |
| `<queries>` 文本块 | ❌ 不使用 | ⚠️ 偶发 |
| 格式一致性 | ✅ 100% 一致 | ⚠️ 不一致 |

**分析**：5-2B 的工具调用格式完全一致（标准 `tool_calls`），而 V-4.5 在不同场景下输出格式不同，增加了下游解析的复杂度。

### 3.4 迭代效率

| 场景 | MiniCPM5-2B 迭代 | V-4.5 迭代 | 效率提升 |
|------|-------------------|------------|----------|
| 2 人烤肉 | 6 | 2 | 3.0x |
| 3 人日料 | 4 | 1 | 4.0x |
| 2 人火锅 | 4 | 3 | 1.3x |
| **平均** | **4.7** | **2.0** | **2.4x** |

**分析**：V-4.5 平均只需 2.0 次迭代完成任务，5-2B 需要 4.7 次。迭代次数直接决定端到端延迟。

### 3.5 响应时间分解

| 场景 | 5-2B 总时间 | V-4.5 总时间 | 5-2B 模型思考 | V-4.5 模型思考 | API 调用时间 |
|------|------------|-------------|-------------|---------------|-------------|
| 2 人烤肉 | 95.4s | 22.8s | ~81s | ~11s | ~14s |
| 3 人日料 | 63.0s | 12.2s | ~47s | ~10s | ~16s |
| 2 人火锅 | 81.3s | 63.4s | ~47s | ~34s | ~35s |

**分析**：V-4.5 的模型推理速度快约 4-5 倍。5-2B 的瓶颈在于每次迭代的思考时间（约 10-15s/次），6 次迭代累积到 81s。

### 3.6 推荐结果质量

| 维度 | MiniCPM5-2B | MiniCPM-V-4.5 |
|------|-------------|---------------|
| **场景 1** | 刘记炙子烤肉（有路线对比） | 汉巴味德（仅列名） |
| **场景 2** | 京都里日式料理（有时间对比表） | 仅列出 6 家餐厅名 |
| **场景 3** | 日坛涮肉（公平性分析） | 海底捞（12 条路线完整对比） |
| **推荐理由充分性** | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| **路线时间对比** | ✅ 有 | ⚠️ 场景 3 有，其余无 |
| **出发时间建议** | ❌ 无 | ❌ 无 |

**分析**：5-2B 的推荐质量更高——场景 2 中提供了完整的时间对比表和出发建议。V-4.5 在场景 3 中表现最好（12 条路线全对比），但在场景 2 中因工具未执行导致推荐缺乏数据支撑。

### 3.7 工具调用格式标准化

| 指标 | MiniCPM5-2B | MiniCPM-V-4.5 |
|------|-------------|---------------|
| 首选格式 | `tool_calls` (OpenAI) | 不固定 |
| 格式漂移 | 无 | 有（3 种格式） |
| 下游解析复杂度 | 低 | 高 |
| 需要 `<tool_call>` 解析器 | 否 | 是 |
| 需要 `<queries>` 解析器 | 否 | 是 |

## 六、与历史基线对比（2026-09-05）

| 指标 | 基线 MiniCPM5-2B (09-05) | 当前 MiniCPM5-2B (09-13) | 当前 V-4.5 (09-14) |
|------|--------------------------|--------------------------|---------------------|
| 成功率 | 100% | 100% | 100% |
| 总工具调用 | 37 | 22 (-41%) | 20 (-46%) |
| 平均响应 | 137.5s | 79.9s (-42%) | 32.8s (-76%) |
| 平均迭代 | 3.0 | 4.7 (+57%) | 2.0 (-33%) |

- **工具调用数下降**：基线（09-05）的 37 次是两个模型的平均值；当前 5-2B 的 22 次更高效（减少了冗余调用）
- **响应时间大幅下降**：从 137.5s → 79.9s（5-2B）/ 32.8s（V-4.5），主要得益于 API 端点优化和模型推理加速
- **迭代次数上升**：5-2B 从 3.0 → 4.7，说明模型更倾向于分步执行（更安全但更慢）

## 七、结论与建议

### 7.1 模型选型建议

| 场景 | 推荐模型 | 理由 |
|------|----------|------|
| **参数敏感型**（坐标、地址） | MiniCPM5-2B-0822 | 参数正确率 100%，无格式错误 |
| **速度敏感型**（用户体验） | MiniCPM-V-4.5 | 响应快 2.4x，迭代少 57% |
| **复杂编排型**（多餐厅对比） | MiniCPM-V-4.5 | 并行 12 路，全量路线计算 |
| **格式稳定型**（下游解析） | MiniCPM5-2B-0822 | 格式 100% 一致 |
| **生产环境** | **编排层 + 任意模型** | 模型只做窄接口，编排由 DAG 保证 |

### 7.2 编排层的必要性

两个模型都存在的共性问题：

| 问题 | 5-2B | V-4.5 | 编排层解决方案 |
|------|------|-------|---------------|
| 并行识别不足 | 严重 | 轻微 | DAG 显式并行 |
| 距离规则误判 | 可能 | 可能 | guard.py haversine |
| 步骤坍缩 | 历史存在 | 轻微 | PlanDagBuilder |
| 格式不一致 | 无 | 严重 | 确定性执行器绕过 |

**结论**：无论选择哪个模型，编排层都是必要的。模型的能力差异可以通过编排层抹平。

### 7.3 后续优化方向

1. **V-4.5 格式适配**：增加 `<queries>` 和 `<tool_call>` 双格式解析器
2. **V-4.5 参数校验**：在编排层增加坐标格式校验，自动修正常见错误（如 `116411` → `116.411`）
3. **5-2B 并行优化**：通过 `step_order_fn` 注入更激进的并行策略
4. **A/B 测试**：在生产环境中同时部署两个模型，根据场景特征动态选择
