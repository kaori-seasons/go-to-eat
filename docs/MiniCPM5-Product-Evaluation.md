## 二、测评背景与方法论

### 2.1 系统简介：Where to Eat 多人聚餐推荐

Where to Eat 是一个多人聚餐推荐系统，核心流程：

```
用户自然语言 → 意图提取 → 地理编码 → 餐厅搜索 → 路线规划 → 公平排序 → 推荐结果
     │              │           │           │           │           │
     │         RuleExtractor   Amap geo   Amap search  Amap route  FairRanker
     │              │                                   │
     └──── MiniCPM（窄接口）                      └── StepGuard（距离规则）
```

支持 5 城市（北京/上海/广州/深圳/厦门）、16 种菜系、多轮指令（换菜系/加人/改时间）。

### 2.2 测评目标与演进路径

```
Phase 1: V-4.5 能否直接用于生产？
         ↓ 发现：格式漂移 + 参数错误
Phase 2: 5-2B 能否替代 V-4.5？
         ↓ 发现：可靠性提升但编排能力不足
Phase 3: 编排层加固能否补齐短板？
         ↓ 结论：能，且综合得分超越 V-4.5
```

### 2.3 评估框架设计

采用 **12 维度 × 3 层级**框架，以生产可靠性为第一优先级：

```
层级 1 — 生产可用性（50%）
  ├── 参数零错误率        15%
  ├── 高德 API 成功率     10%
  ├── 工具调用格式一致性   10%
  ├── 步骤执行完整率       10%
  └── 端到端成功率          5%

层级 2 — 推荐质量（30%）
  ├── 路线计算覆盖率       10%
  ├── 推荐理由充分性       10%
  ├── 公平性分析深度        5%
  └── 输出信息量            5%

层级 3 — 效率（20%）
  ├── 响应时间             10%
  └── 迭代效率             10%
```

## 三、Phase 1：V-4.5 基线测试——发现问题

### 3.1 测试场景

| 场景 | 输入 | 难度 |
|------|------|------|
| 2 人烤肉 | 望京+霍营出发，吃烤肉 | 低 |
| 3 人日料 | 国贸+中关村+五道口，19点到 | 中 |
| 2 人火锅 | 天通苑+三里屯，公平推荐 | 中 |

### 3.2 逐场景执行分析

#### 场景 1：2 人烤肉

```
V-4.5 执行路径：
迭代1: geo×2 + driving×2 + search  → 5 calls（并行）
迭代2: 生成推荐（汉巴味德）
总耗时: 22.8s
```

**问题**：destination 坐标为 `116411.0926,39.9774`（经度多出 `116` 前缀），2 次 driving API 返回失败。API 成功率仅 60%。

#### 场景 2：3 人日料

```
V-4.5 执行路径：
迭代1: 输出 <queries>...</queries> 块（11 个工具调用）
        → 未被框架解析，0 次实际执行
        → 直接进入最终响应（仅列出餐厅名，无路线时间对比）
总耗时: 12.2s（但 0 次有效 API 调用）
```

**问题**：模型退化为非标准输出格式，11 个工具调用全部丢失。推荐"京都里日式料理"但无任何路线数据支撑——本质是"盲推"。

#### 场景 3：2 人火锅

```
V-4.5 执行路径：
迭代1: geo×2 + search              → 3 calls（并行）
迭代2: driving×12（2人×6餐厅）     → 12 calls（并行）
迭代3: 生成推荐（海底捞）
总耗时: 63.4s
```

**表现**：此场景 V-4.5 表现最好——参数全部正确，并行 12 路全量路线计算，公平性分析完整。

### 3.3 V-4.5 能力画像

```
能力维度            V-4.5 得分       评级
─────────────────────────────────────────────
并行执行            ████████████  12 路  ✅ 强项
响应速度            █████████░░░  32.8s  ✅ 强项
路线覆盖率          █████████░░░  44%    ✅ 合格
参数正确率          ████████░░░░  80%    ⚠️ 不稳定
格式一致性          ████░░░░░░░░  漂移   ❌ 隐患
步骤执行完整率      █████░░░░░░░  63%    ❌ 短板
```

### 3.4 Phase 1 结论

V-4.5 的**并行能力**和**响应速度**是显著优势，但存在两个致命隐患：

1. **格式漂移**：同一模型在不同场景下输出 `tool_calls`、`<tool_call>`、`<queries>` 三种格式，下游解析器无法预知输入格式
2. **参数错误**：坐标格式 `116411.0926` 导致 API 调用失败，错误率 20%

**决策**：切换到 MiniCPM5-2B，优先解决可靠性和格式一致性问题。

## 五、Phase 3：MiniCPM5-2B + Hardening——编排层加固

### 5.1 IGID 记忆系统移植方案

将 IGID（Infinite-Genre-Instance-Dungeons）的五项记忆系统能力移植为独立编排层：

| IGID 能力 | 编排域映射 | 解决的问题 |
|-----------|-----------|-----------|
| 记忆图谱 | Plan DAG | 步骤坍缩：9步流程只完成1步 |
| 未闭合话题追踪 | pending steps | 步骤遗漏 |
| 召回注入 | 投影 ≤1200 token | 多轮上下文丢失 |
| 作用域隔离 | Session scope | 会话串线 |
| 规则前置层 | StepGuard | 距离规则误判 |

### 5.2 编排层架构

```
┌─────────────────────────────────────────────────────────┐
│                    用户聚餐请求                           │
└─────────────────────┬───────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────────────────┐
│              RecommendationPipeline                      │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌────────┐ │
│  │Extractor │→ │DAG Builder│→ │ Executor │→ │ Ranker │ │
│  │ 意图分解  │  │ 计划物化  │  │ 确定性执行│  │公平排序│ │
│  └──────────┘  └──────────┘  └──────────┘  └────────┘ │
│       ↕              ↕             ↕                    │
│  ┌──────────────────────────────────────────────────┐  │
│  │  StepGuard │ EntityCache │ SessionTrace │ Recall │  │
│  │  规则校验   │  实体缓存   │  结构化 trace │投影注入│  │
│  └──────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────┘
```

**核心设计原则**：模型降维——将开放式编排问题降维为封闭式识别问题。模型仅负责语义理解（提取城市/菜系/地点），编排由确定性 DAG 保证。

### 5.3 四类 Bad Case 修复

| Bad Case | 现象 | 根因 | 编排层解决方案 |
|----------|------|------|---------------|
| 步骤坍缩 | 9步流程只完成1步 | 模型无法维护完整计划 | PlanDagBuilder 显式 DAG |
| 依赖跳步 | 用地名直接调路线 | 缺少运行时坐标校验 | StepGuard haversine 守门 |
| 并行识别失败 | 3个geo串行执行 | 模型无法判断并行 | DAG 显式并行依赖 |
| 分支误判 | 8km还调骑行路线 | 缺少距离规则前置层 | guard.py 距离规则 |

## 八、结论与创新点

### 8.1 核心结论

MiniCPM5-2B 通过两阶段演进（可靠性升级 + 编排层加固），在以生产可靠性为优先的评估框架下实现了质的飞跃：

```
┌──────────────────┬──────────┬──────────┬──────────┬──────────┐
│     能力维度      │  V-4.5   │  5-2B    │ 5-2B+加固 │   评级    │
├──────────────────┼──────────┼──────────┼──────────┼──────────┤
│ 参数正确率        │   80%    │  100%    │  100%    │ ⚠️ → ✅+ │
│ 格式一致性        │  漂移    │  一致     │  一致     │ ❌ → ✅  │
│ 端到端完成率      │  ~100%   │  ~100%   │  100%    │    —     │
│ 编排正确性        │   N/A    │   68%    │  100%    │ ❌ → ✅  │
│ 并行识别          │   N/A    │   45%    │  100%    │ ❌ → ✅  │
│ 公平评估得分      │  7.15    │  7.65    │  7.70    │ ▲ +0.55 │
└──────────────────┴──────────┴──────────┴──────────┴──────────┘
```

### 8.2 适用场景推荐

| 场景 | 推荐方案 | 理由 |
|------|----------|------|
| 多工具编排 | 5-2B + 编排层 | 可靠性 + 完整性最优 |
| 简单单轮调用 | V-4.5 | 速度优先 |
| 高可靠生产 | 编排层 + 任意模型 | 编排层兜底 |

### 8.3 创新点总结

1. **IGID → 编排域跨领域移植**：首次将游戏 AI 记忆系统能力移植到工具编排场景
2. **模型降维策略**：将开放式编排问题降维为封闭式识别问题
3. **确定性 + 模型窄接口**：编排层保证正确性，模型仅负责语义理解
4. **公平评估框架**：12 维度 × 3 层级，以生产可靠性为第一优先级
